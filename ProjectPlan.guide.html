What MDM does

and what it does not do

MDM does

  • Manage eight resource families for each partner and each school year: EdOrgs, Descriptors, Programs, Assessments, Chart of Accounts, Certifications, Descriptor Mappings, Courses. Courses are opt-in: a state catalog is managed; locally defined courses stay read-only; course offerings and sections stay out.
  • Keep each year as its own set. Roll a year forward. Map records across Ed-Fi versions.
  • Route each push to the correct ODSs with the SBAA tags School_Year, EA_Tenant, Environment_Type. Block incompatible targets.
  • Write only through the ODS/API. The Ed-Fi rules block unsafe changes.
  • Review each change (draft → review → publish). Approve each push as an immutable manifest, then apply.
  • Pull from a partner's upstream system of record through its HTTP API.

MDM does not

  • Touch student, staff, or transactional data.
  • Create or delete SBEs, tenants, or ODSs. SBAA does this.
  • Write SQL into an ODS.
  • Push on a schedule. A person approves and applies each manifest.
  • Delete anything it did not explicitly tombstone. Set differences never produce deletes.
  • Keep its own users, roles, or ODS credentials. SBAA owns all three.

Where it lives

Two deployables, packages/mdm-api and packages/mdm-fe, in the SBAA monorepo. Own Postgres. Same IdP, teams, roles, and UI library as SBAA.

How a change travels

one pipeline · each stage adds to it · no stage rewires it

IntakeImport from an ODS. Import a file. Edit in the UI. Pull from upstream. All land in a draft.
Change requestOne batch of edits in one year set. Submit freezes the batch.
ReviewAn approver who did not contribute reads one diff. Approve or reject the batch.
PublishedJSONB store + version history, in the year set's pinned Ed-Fi shape.
TargetsResolve from SBAA tags over ODSs the team owns. Fingerprint each. Block incompatible ones.
ManifestRead the ODS. Compute create / update by owned fields. Deletes only from approved tombstones. Freeze targets, payloads, ETags.
ApplyA publisher applies one manifest through the ODS/API in dependency order, with If-Match.
RunRecord each outcome: ok, failed, skipped, conflict, uncertain. Re-run finishes the same manifest.

SBAA provides

Teams, roles, tags, topology, one MDM application per ODS, and custody of its credentials. New endpoints: identity, targets, application ensure, credential read and rotation, namespaces.

mdm-api provides

Year sets, records, managed scopes, change requests, manifests, runs, and the drift scan — on its own database and job queue. It calls SBAA with a least-privilege service identity.

Tooling provides

sbaa_api_client gets MDM wrappers and an mdm_api_base_url setting. Scripts can import, build manifests, and apply without the UI.

Stage 0 — Foundations

build what every later stage assumes · M

SBAA API
  • Add the roles mdm-editor, mdm-approver, mdm-publisher, mdm-admin by migration.
  • Add the identity endpoint. Add application ensure per ODS with SBAA-held credentials. Add the service-only credential read and rotation.
  • Add owned-ODS target listing with fingerprints. Add the partner namespace setting.
mdm-api
  • Create the NestJS package with its own TypeORM datasource and its own pg-boss schema.
  • Use a host-scoped cookie-session BFF. Resolve identity through SBAA. Use bearer tokens only for service calls. Reject cross-origin mutations.
  • Create year sets, records, versions, managed scopes, change requests with contributors, change items, manifests, runs, and run records.
  • Build the registry from the pinned OpenAPI document, one entry per concrete descriptor endpoint.
mdm-fe
  • Create the React package on common-ui. Reproduce the SBAA chrome. Wire the login.
Infra
  • Add the MDM Postgres, the Keycloak mdm client with the API callback, and the Nx serve targets to local dev.
  • Create the deployed database, pipeline, and Secrets Manager access.

Stage 0 is bigger than a scaffold because SBAA must ship the identity endpoint, credential custody, and roles before any MDM code can authenticate or push. The resource registry also starts here so every later job is generic from day one.

Stage 1 — Descriptors slice

the full pipeline for the simplest family · EA internal pilot · L

mdm-api
  • Add year sets. Fingerprint each target. Block incompatible targets.
  • Add the import job with count-drift detection and write-shape normalisation. Write the result as a change request inside managed scope.
  • Add the change-request lifecycle: base revisions, frozen batches, CAS approval, contributor-based separation of duties.
  • Build immutable manifests: owned-field updates, tombstone-only deletes, observed ETags, target fingerprints.
  • Apply one manifest at a time with If-Match. Suspend a target whose fingerprint changed. Order by /dependencies.
  • Record ok, failed, skipped, conflict, uncertain. Re-run the same manifest only. Reconcile uncertain by natural key first.
mdm-fe
  • Build the inbox Home and the Descriptor editor.
  • Build the review screen with one batch diff.
  • Build target confirmation, manifest preview, and run results.
sbaa_api_client
  • Add mdm_api_base_url.
  • Add year-set, target, record, change-request, import, manifest, apply, run, and re-run wrappers.
Validation
  • Record HTTP fixtures (DS 5.2 with and without TPDM). Run one nightly end-to-end test against the pilot dev ODS, including a conflict case. Do not run an ODS/API in CI.
  • Run bulk reads in the agreed writer-quiescence window. Run the review-UX UAT.

Descriptors go first because they are flat, fully MDM-owned, version-stable and dependency-light — they touch every layer with the least UI, and they surface feedback on the review workflow, the riskiest UX decision, earliest.

✓Pilot: EA's internal tenant on ODS/API 7.3 / Data Standard 5.2 with TPDM, MDM application unprofiled, current school year.

Stage 4 — Stretch: drift scanning

the manifest build, read-only, on a timer · S · any time after Stage 1

mdm-api
  • Add a scheduled per-partner scan that reuses the manifest build in read-only mode. Persist drift reports.
  • Add per-partner settings: opt-in, schedule, scope. Add an optional approver notification.
mdm-fe
  • Flag drifted records. Build the drift report screen.
Docs
  • Write the off-peak schedule guidance. Measure the ODS read load.

Why it can wait

  • The scan is read-only. It never produces an approved manifest. It never applies.
  • It reuses Stage 1's manifest builder. It adds a schedule and a report table only.
  • Each scan reads every ODS once. Keep it opt-in and off-peak.

Release order

two deployables, one sequence

1 · SBAAMigration: roles, credential table. Privileges. /mdm endpoints. Backward compatible; no MDM dependency.
2 · ProvisionEnsure one application per pilot ODS. Verify the claimset fingerprint and effective access with one GET.
3 · MDMSchema migrations. Own pg-boss schema on the MDM connection. Workers. Queue payloads carry a schema version; old workers reject newer payloads.
4 · EnableFeature flag per team. Year sets cannot be created without it.

Rollback

MDM workers stop independently. SBAA endpoints are additive. A claimset version bump always ships in step 2 before the MDM release that needs it.

Capability checks run first

Readiness rejects a missing claimset version, a profiled application, or an incompatible fingerprint before a push starts — never halfway through one.

Risks and mitigations

what can go wrong, and what we do about it

RiskMitigation
Untagged ODSs are invisible to MDM.Audit the tags before each stage. Show the target list before each push. Block incompatible targets.
The change-request UI is the largest and riskiest UX.Validate it with the internal pilot in Stage 1. Scale it after that.
Partial pushes occur. The ODS/API is non-transactional.Persist per-operation outcomes. Record skip reasons. Re-run the same manifest only. Never pretend to roll back.
Cross-version mappings are hand-maintained.Write them only for the version pairs StartingBlocks runs. Apply them only at roll-forward.
Writer quiescence is an agreement, not a guarantee.Count-drift abort is the safety net. Revisit snapshot reads with the first external partner.
The first external partner may run a different release or profiles.The fingerprint check blocks, never warns.
Claimsets cannot lock single fields.Document the limit. Use the ownership merge for EdOrgs.

Future scope

not v1 — recorded so v1 keeps the seams open

Standalone MDM for data outside StartingBlocks

Manage master data for Ed-Fi targets StartingBlocks does not host: a district's self-hosted ODS/API, another vendor's hosted instance, a state or collaborative ODS.

What changes

  • Targets come from an MDM-owned registry, not SBAA tags.
  • Credentials are MDM-owned, entered by the partner's admin.
  • Identity is MDM-owned or federated; delegation to SBAA stays for partners who are SBAA teams.
  • Target health check replaces tag discipline.

What does not change

Records, change requests, manifests, runs, ownership, roll-forward, drift — all take a list of targets and never ask where it came from.

Seams v1 keeps

  • A TargetProvider interface with one implementation today.
  • Target identity is URLs + fingerprint; SBAA ids live under provider.
  • The authorization guard reads a privilege map and nothing else knows SBAA produced it.
  • Manifests and runs take targets, never ODS ids.

Also deferred

  • Direct-database upstream sources.
  • Embedding mdm-fe inside the SBAA shell.
  • Per-partner field-ownership overrides.
  • Effective-dated (bitemporal) records.
  • Non-Ed-Fi targets — the Ed-Fi API is the safety model this design depends on.
